# e2e-failure-analyzer

## Trigger Conditions

Root-cause analysis and failure clustering after a test failure in an openAN repository, or running /e2e-failure-analyzer.

## Analysis Process

1. **Evidence extraction**: collect failed case names, assertions, stack traces, and environment information (language, command, commit SHA) from the runner's structured output / JUnit XML / Playwright report / logs
2. **Clustering**: group cases with the same error signature (key stack frames + normalized assertion text) into the same cluster to reduce duplicate analysis
3. **Root-cause classification** (give a verdict and confidence for each cluster):

   | Classification | Criteria (meeting any one suffices; cite the evidence) |
   | --- | --- |
   | E2E_CODE_BUG | Wrong assertion, broken selector, mock not matching the real protocol, shared state between cases |
   | SOURCE_BUG | Behavior of the code under test contradicts the documentation/protocol commitment (attach protocol clause or API documentation reference) |
   | ENV_INFRA | Service not ready, port/network issues, missing dependencies, Docker unavailable |
   | FLAKY_TIMING | Timing-sensitive: passes on rerun, timeout boundary, insufficient async waiting |
   | INSUFFICIENT_INFO | Evidence insufficient to support any of the above classifications |

   > Assertions on LLM-dependent cases must be based on status codes/structure/process state, not on directly asserting model-generated text (test-plan §3.3); if a failure stems from asserting the wrong object (asserting generated text), treat it as E2E_CODE_BUG and do not count it as a real failure.

4. **Cross-language note**: for A2A-T interop failures, determine whether the cause is on the Java side, the Python side, or protocol sample inconsistency (`a2a-t-corpus` data drift)

## Output (invocation text for follow-up skills)

- Structured conclusions (Markdown table: cluster, cases, classification, confidence, key log summary)
- Follow-up invocation text generated by classification:
  - SOURCE_BUG → input draft for `github-issue-creator`
  - E2E_CODE_BUG → fix instruction for `e2e-test-regression` (including test file paths and verification commands)
  - ENV_INFRA / FLAKY / insufficient info → diagnosis and evidence-collection suggestions

## Hard Constraints

- Do not execute commands directly, do not modify code, do not create Issues, and do not write back to any platform
- Evidence references must include file paths with line numbers or log line numbers; conclusions must not be drawn from guesswork
