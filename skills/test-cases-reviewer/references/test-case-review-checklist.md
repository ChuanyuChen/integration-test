# Test Case Review Checklist

**Core principles: atomicity, repeatability, traceability, completeness, independence**

**Template baseline**: the 16-column header is exactly the official template `Milestone,Case Name,Case ID,Module,Component Deps,Requirement Link,Case Type,Priority,Precondition,Steps,Expected Result,Automatable,Automated Test,Dev Owner,Test Owner,Notes`; column order and count must match the template, otherwise the template is non-compliant. Milestone format is `<YY>-<season>` (e.g. `26-winter`), corresponding to the archive directory of the same version as the test plan.

| **Case ID** | Mandatory | The ID is unique within the repository | [Rule]The case ID is unique within the repository<br>[Rule]Format `[FIT-<feature>-<topic>-<3-digit seq>]` / `[DFX-<feature>-<topic>-<3-digit seq>]` (wrapped in square brackets), e.g. `[FIT-registry-center-agentcard-001]`; feature = feature/repo name (lowercase kebab-case matching the "Module" column), topic = functional/non-functional scenario (lowercase kebab-case) | |

| **Case Type** | Mandatory | The type field is filled accurately | [Rule]Fill the official English enum: main path/deployment/config/state transition → `Functional Test`; business-level negative cases, boundary values, concurrency/idempotence exceptions → `Exception Test`; A2A-T protocol primitives → `Protocol Test`; DFX rows map from the `dfx_type` key in Notes: DFT/DFD→`Functional Test`, DFS→`Deployment Test`, DFR→`Stability Test`, DFP→`Performance Test` (stress scenarios `Stress Test`), DFNS→`Security Test`, DFC→`Compatibility Test`; one case has only one type | |

| **Priority** | Mandatory | The level is filled reasonably | [Rule]Levels are assigned accurately and meet the general ratio requirements<br>  P0: feature acceptance cases — deployment readiness success, core functional forward main flow (in the DFX table: core observability/serviceability main path)<br>  P1: feature basic-function cases — inheriting basic feature functions and covering most requirement specs (in the DFX table: key diagnostics and reliability)<br>  P2: feature complex scenarios and business-level exceptions/negatives (the FIT table only indicates business-scenario priority and **contains no DFX cases**; probes/logs/self-healing/performance/security/compatibility go into a standalone DFX table) | |
| | Suggested | Review whether the overall level ratio is reasonable | | |
| **Precondition** | Mandatory | Describes the pre-configured parts, such as test environment and data configuration | [Rule]Preconditions state the concrete test environment, data configuration, and current system state (software, hardware, network environment)<br>[Rule]Make environment elements explicit, e.g. specify compose service components and versions, ports, auth tokens, preset test data.<br>[Rule]Each statement must be prefixed with a sequence number in the form "Arabic numeral" + "separator". | **Steps** | Mandatory | Each test step is prefixed with a sequence number | [Rule]Each test step must be prefixed with a sequence number in the form "Arabic numeral" + "separator"<br>[Rule]If the operation result needs to be checked, append "see result xx" after the step, where xx is the number in "Expected Result"<br>[Rule]If an expected result can only be judged after several consecutive test steps complete, describe "see result xx" after the consecutive steps. | | Mandatory | Every step is executable and unambiguous | | |
| | Mandatory | Steps whose results need checking end with "see result xx" | | |

| | Mandatory | The last step is a cleanup action (Framework §6.3) | [Rule]The last step of the steps must be a cleanup action: delete test data/services created by this case, restore modified configurations, clear injected faults and temporary containers; the expected result must contain a corresponding objectively verifiable assertion | 1. | **Automatable** | Mandatory | P0/P1 must be `Yes` (Framework §4.3.1 acceptance; §8.1 TRR entry) | [Rule]The "Automatable" column is filled with `Yes`/`No`; P0/P1 rows must be `Yes` (TRR entry requirement); P2 may be `No` but the reason must be stated in Notes; the "Automated Test" column is left empty at generation time and backfilled by e2e-test-code-gen | 1. P0/P1 filled `No` with no explanation<br>2. Values other than `Yes`/`No` |
| **Notes** | Mandatory | All orchestration keys are present | [Rule]The Notes column carries orchestration keys as `key:value` pairs, multiple keys separated by `;` (or `;`):<br>  · `design_method:xxx` (required to be annotated per Authoring Guide §2)<br>  · `language_profile:python\|java\|js\|shell` (required for every case; default to the main language of the repo under test; for cross-component cases use the language of where the test is implemented; consumed directly by `e2e-test-code-gen`)<br>  · `protocol_primitive:none\|Task-T\|Notification-T\|Negotiation-T\|Authorization-T` (required primitive for cases involving the A2A-T protocol, otherwise `none`; do not invent primitive names)<br>  · `execution_strategy:smoke\|full\|slow` (consumed by e2e-test-code-gen and CI trigger filtering)<br>  · `environment:<runtime environment>` (required for every case; Framework §6.4 environment dimension, e.g. `docker-compose`, `with-workload-cluster`, `online`, `offline`, for CI environment filtering)<br>  · DFX rows additionally require `dfx_type:DFT\|DFD\|DFS\|DFR\|DFP\|DFNS\|DFC`<br>May also contain verification-point sources, material differences, to-be-confirmed items, and non-automatable reasons. The 5th column `component_deps` is a standalone column (not a Notes key) and is checked per its mandatory items | 1. language_profile empty or outside the enum<br>2. A2A-T case with protocol_primitive filled as none<br>3. DFX row missing the dfx_type key<br>4. Invented primitive names |
| | | Optional supplements: design method, verification-point source, to-be-confirmed items | Fill the "Milestone" column (format `<YY>-<season>`, e.g. `26-winter`) when the user provides a milestone; "Automated Test" is backfilled by the automation phase; per-case review does not check the free-text content of these two types | |
| **Test Case File Naming Convention** | Mandatory | Repo and feature are explicit | [Rule]Standard naming (version segment may be omitted):<br>Feature-level integration test cases:<br>[version_]`<target repo>_<feature>`-fit-test-cases<br>DFX test cases:<br>[version_]`<target repo>_<feature>`-dfx-test-cases<br>Example:<br>registry-center_agent-registration-fit-test-cases<br>registry-center_agent-registration-dfx-test-cases | |
| **Requirement Compliance** | Mandatory | Requirement coverage | Test cases cover 100% of all functions required by the original requirements with no requirement misunderstanding; test cases cover all test points and all known user usage scenarios | |
| | Mandatory | Scenario coverage | Covers normal scenarios, exception scenarios, functional interaction scenarios, etc.; the goal of the test cases is clear and satisfies all aspects of software quality. When FIT and DFX are in separate tables: FIT covers business functional correctness and DFX covers non-functional design capabilities; mixing and cross-table duplication are prohibited (see fit-dfx-scenario-attribution-criteria) | |
| | Mandatory | Scenario attribution | [Rule]Judge by verification target: business functional correctness belongs to FIT; probes/logs/metrics/self-healing/performance/security/compatibility belong to DFX. The FIT table must not contain DFX scenarios such as process/container self-healing, degradation under insufficient resources, or dependency fault recovery; the DFX table must not copy FIT with business results as the only assertion | FIT mixed with DFX scenarios; DFX detailing FIT copies |
| | Mandatory | Cross-table deduplication | [Rule]When both FIT and DFX tables exist, the same triggering operation with the same assertion focus must not be duplicated across the two tables; legitimate coexistence with different assertion focuses is allowed | Fault-injection recovery appears once in each table with different classifications but the same assertion |
| | Suggested | Annotate the design method used for complex scenarios | | |
| **DFX Coverage** | Mandatory | DFX dimension coverage is complete | [Rule]All applicable DFX dimensions have corresponding cases. The DFX dimensions are:<br>  DFT testability, DFD diagnosability, DFS serviceability, DFR reliability, DFP performance, DFNS security, DFC compatibility<br>[Rule]Dimensions that are not applicable need a stated reason (derive covered dimensions from the dfx_type key in Notes and the case IDs) | 1. Only some DFX dimensions covered<br>2. No reason given for non-applicable dimensions |
